2. How resting + countdown are driven
- Signal: useSetLoggingOrchestrator.shouldOpenRestTimer (unchanged), after a set log when not the last set of the block.
- Bridge: InCardRestBridge (inside LiveRestTimerProvider) acks the signal and calls startRest with rest_seconds from restStartRef (filled by handleSetComplete / handleLastSetLoggedForRest) plus next set numbers.
- Tick: LiveRestTimerProvider keeps a deadlineMs; a 250ms interval + visibility/focus handlers recompute secondsLeft = max(0, ceil((deadline - now)/1000)). Never negative.
- UI: LiveCard reads context → status ● Resting (green); auto-injects LiveCardGlue “↺ resting — Set N next” + countdown in .t. Superset/Giant pass restGlue="none" and feed the same into their existing glue slot.
- Skip: LiveCardLogField / LiveCardLogButton call skipRest on focus/change/click so logging is never blocked behind the countdown.

3. Reload / resume approach
- On startRest, persist { deadlineMs, nextSetNumber, totalSets, pendingAction, setEntryId } to sessionStorage key df:live-rest:{sessionId}:{setEntryId}.
- On provider mount / setEntry change: if deadline already past → clear storage and do not rest. Else resume with remaining seconds from the deadline (wall clock), never a stuck or negative countdown.
- Backgrounding: same deadline math on visibility/focus — no interval-only decrement.
