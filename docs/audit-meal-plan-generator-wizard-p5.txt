## PART 2 — The 3 steps

### Step 1 — Targets (`step === 1`)

**Purpose:** Name the plan and set daily macro/structure targets.

**Controls:**
- Plan name — text `Input` (optional; defaults to "Generated Meal Plan" at generation)
- Daily calories — number `Input` (required, min 800, max 6000; default 2000)
- Macro mode — toggle pills: **Auto-Calculate** | **Manual**
  - Auto: read-only grid showing `autoMacros(targetKcal)` protein/carbs/fat/fiber in bordered mini-cards
  - Manual: four number inputs + kcal-sum validation banner (success/warning with CheckCircle2/AlertTriangle)
- Meals / day — `<select>` 3–6 (default 4)
- Options / meal — `<select>` 1–3 (default 3)
- **Next** — `setStep(2)`; disabled if `targetKcal < 800`

**No Generate on step 1.** No client assignment.

---

### Step 2 — Food Rules (`step === 2`)

**Purpose:** Dietary constraints, meal-style preferences, food include/exclude lists.

**Controls (four `GlassCard` sections + footer bar):**

1. **Dietary Restrictions** — checkbox-style preset buttons from `restriction_presets` table; derives `excludedTags`; shows tag chips when selected. Loading spinner until `sessionReady` + presets load.

2. **Meal Styles** — per-type `<select>` from `MEAL_STYLE_OPTIONS` constant:
   - Breakfast, Lunch, Dinner always
   - Snack only if `mealCount >= 4`
   - Values map to generator `breakfastStyle` / `lunchStyle` / etc.

3. **Exclude Specific Foods** — `FoodSearchBox` + removable pill chips (error-colored)

4. **Required Foods** — `FoodSearchBox` + removable pill chips (success-colored)

**Footer:** **Back** → step 1 | **Generate Plan** (Sparkles icon) → `handleGoToReview()`

**Generate trigger:** `handleGoToReview` sets `step(3)` and immediately calls `runGeneration()` (L531–534). There is no separate "review before generate" — generation starts on entering step 3.

---

### Step 3 — Review (`step === 3`)

**Purpose:** Show generation progress, errors, editable preview, save.

**States (mutually rendered sections):**

| State | UI |
|-------|-----|
| **Generating** (`generating === true`) | Centered `GlassCard`: Loader2 in cyan-tinted circle, copy "Generating your meal plan…", subtext, **Cancel** button (`cancelGeneration`) |
| **Error** (`!generating && generationError`) | Error card with split message lines, **Back** (step 2), **Retry** (`runGeneration`) |
| **Success** (`!generating && result`) | Summary card + expandable meal cards + bottom action bar |

**Review / edit UI (on success):**
- Summary: plan name, raw-portions notice (emoji badge), tolerance pill, kcal + fiber pills, **Regenerate** + **Save Plan** (top)
- `MacroBar` ×4 (protein/carbs/fat/fiber vs targets)
- Warning list (if `result.warnings`)
- Per-meal `GlassCard`: accordion header (meal index badge, name, per-meal target line, option kcal)
  - Expanded: option tabs (if >1 option), template name, **HTML table** of foods via `FoodRow` (portion ±5g, swap icon), totals row, per-macro deviation pills
- Bottom bar: **Back to Rules**, **Regenerate**, **Save Plan**

**Save:** `handleSave` merges `localOptions` into `result`, calls **`saveGeneratedPlan(mergedResult, user.id)`**, toast, `router.push(/coach/nutrition/meal-plans/${planId})`.

**Post-save edits before save:** `adjustPortion` / `swapFood` (client-side via service helpers) + swap modal listing `getSwapAlternatives(...)`.

**Loading/streaming:** **No streaming.** Single POST, blocking spinner until JSON returns or 60s abort. Cancel sets `cancelledRef` and shows error string (does not abort fetch server-side — UI-only cancel).

## PART 3 — Shell & layout

### Overall structure

```
ProtectedRoute (coach)
  AnimatedBackground
    [FloatingParticles — opt-in]
    CoachPageShell (default-5xl, px-4 sm:px-6)
      Header row: h1 "Meal plan generator" + text Back link → /coach/nutrition
      Step nav bar: 3 × (StepIndicator + label) + hairline connectors (sm+)
      Step content (conditional step 1 | 2 | 3)
      Swap modal (fixed overlay, conditional)
```

**Not a modal wizard.** Full route with stacked card sections.

### Width treatment

| Surface | Shell variant | Effective width |
|---------|---------------|-----------------|
| **Generator (current)** | `CoachPageShell widthVariant="default-5xl"` + `px-4 sm:px-6` | **max-w-5xl (~1024px)** — centered column |
| Nutrition workspace | `data-7xl` | max-w-7xl (1280px) |
| Plan builder (post P2 follow-up) | `canvas-full` | full viewport, page-level gutters |

**Finding:** Generator is **narrower than both** the nutrition workspace and the full-width builder. Step 3's food table will feel cramped on wide monitors relative to peer surfaces. P5 should decide: `canvas-full` (match builder station) or `data-7xl` (match workspace) — not stay on `default-5xl` unless intentional form-wizard narrowness (`form-2xl` is even narrower per 95-STANDARD).

### Step indicator

**Current:** Horizontal **numbered circles** (1–3) with checkmark when complete; active step = filled `--fc-accent-cyan` circle; inactive = `--fc-glass-border`. Labels "Targets / Food Rules / Review" in `text-xs font-medium` beside each circle. Between steps on `sm+`: flex `h-px` hairline connectors.

**Not** tabs, not a progress bar, not mono uppercase stepper like mockup `.mono` chips. This is custom inline JSX — primary wizard chrome needing system-native treatment.

## PART 5 — Reskin vs redesign judgment

### Verdict: **Cleanly reskinnable** — structure is sound; primary work is tokens + chrome + alignment with nutrition surfaces.

**Why reskin (not redesign):**
- The **3-step flow is logical** and matches coach mental model: targets → constraints → generate/review/save.
- **Step boundaries and validation gates are clear** (kcal min on Next; Generate only from step 2; review states are well-separated).
- **Logic is already extracted** to `mealPlanGeneratorService.ts` + API route; the page is a fat but coherent view layer.
- No fundamental UX conflict with the design system — the mockups describe **how** nutrition content should look, not a different wizard paradigm.

**What pushes toward “presentation refactor” (still not a full redesign):**
- Step 3 review **layout grammar diverges** from the plan builder (table + GlassCard accordion vs badge·name·mono + macro strip). Matching builder display components (`PlanMacroStrip`, meal row patterns from `meal-display/`) is **structural presentation work**, but can be done **without touching generation/save logic** — reuse read-only/display components with existing adjust/swap handlers wired to the same props.
- **Monolithic single file** (~1300 lines) makes reskin tedious but is an organization concern, not a behavior change. P5 can restyle in place or extract presentational sub-components — either is reskin if handlers/config/save path stay frozen.

**Load-bearing tangles (restyle carefully — do not “fix” behavior in P5):**
| Area | Risk |
|------|------|
| `FoodSearchBox` portal positioning | Clipping fix depends on `fixed` + `getBoundingClientRect`; restyle dropdown shell without changing open/close/blur timing |
| `handleGoToReview` = step 3 + immediate `runGeneration` | UI must keep this coupling; don’t add a “review config” interstitial without product sign-off |
| `localOptions` merge before `saveGeneratedPlan` | Save path must still merge edits; restyle table rows only |
| `getSwapAlternatives` rendered in swap modal map | Keep slotType/foodId inputs identical |
| 60s `AbortController` + `cancelledRef` | Loading UI only; don’t change timeout semantics |

**Not P5 (logic observations only):**
- `requiredFoodIds` collected in UI but **unused in generator engine** (documented in `MEAL_PLAN_GENERATOR_AUDIT.md`). Reskin should keep the Required Foods UI unless product removes it separately.

### Recommended P5 approach

1. **Reskin in place** on `page.tsx` (or extract presentational components into `src/components/coach/nutrition/generator/` — presentation only).
2. **Align shell width** with builder (`canvas-full`) or workspace (`data-7xl`).
3. **Replace GlassCard stacks** with open sections + hairlines; borrow classes from `coachNutritionWorkspace.module.css` and `mealDisplay.module.css`.
4. **Step 3:** Consider reusing `PlanMacroStrip` + meal row patterns for coherence with `/coach/nutrition/meal-plans/[id]` — still reskin if handlers unchanged.
5. **Glow budget:** primary glow on **Generate Plan** and **Save Plan** only.
6. **No mockup required** for product sign-off if P5 follows coach-02 + coach-05 patterns; optional lightweight mockup only if step indicator treatment needs stakeholder preview.
