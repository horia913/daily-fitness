## PART 2 — Data & per-client fields

### Fetch path (confirmed)

**Single API:** `GET /api/coach/clients` — `src/app/api/coach/clients/route.ts`

Assembly (unchanged logic, documented for fences):

1. `clients` table — `client_id, status, created_at, coach_id`
2. `profiles` — name, email, `avatar_url`
3. `getClientMetrics(clientIds)` — `src/lib/coachDashboardService.ts`
4. `fetchCoachAthleteScoreSummariesByClientIds` — latest `athlete_scores` row + paused flag
5. `fetchCoachClientListTrainingPayload` — `src/lib/coachClientListTrainingStatus.ts`

### API response shape per client (confirmed)

| Field | Source |
|-------|--------|
| `id`, `client_id`, `coach_id` | `clients` |
| `status` | `clients.status` |
| `name`, `email`, `avatar`, `firstName`, `profiles` | `profiles` |
| `athleteScore` | `{ score, tier, paused }` or `null` |
| `pauseStatus`, `hasActiveProgram`, `activeProgramAssignmentId` | training payload |
| `trainingStatus` | `on_track` \| `behind` \| `missed_week` \| `paused` \| `no_program` |
| `priorWeekScheduledCount`, `priorWeekCompletedCount`, `currentWeekCompletedCount`, `currentWeekScheduledPastCount` | training payload |
| `metrics` | `ClientMetrics` (see below) |

**Not returned today:** `created_at` / join date (fetched from DB but dropped in mapper).

### `ClientMetrics` fields (from `getClientMetrics`)

| Field | Real / derivable / gap |
|-------|------------------------|
| **name** | **Real** — profiles |
| **avatar / initials** | **Real** — `avatar_url` on profile; UI uses first char of name + `ClientAvatar` severity |
| **join date** | **Real in DB** (`clients.created_at`) — **not on list API** (would-need-data to expose) |
| **roster status** | **Real** — `clients.status`: `active`, `inactive`, `pending` (confirmed on coach roster). Type also lists `at-risk` but **list API does not set it** — `at-risk` is computed on **detail** summary only |
| **assigned program + week progress** | **Real** — `metrics.activeProgramName`, `programCurrentWeek`, `programDurationWeeks` from active `program_assignments` + instance week resolver |
| **assigned meal plan** | **Real in DB** (`meal_plan_assignments`) — **not on list API** (no plan name/id in response). Only **nutrition signal on list:** `metrics.mealCompliance7dPct` |
| **training adherence % (recent)** | **Derivable on list** — not a stored field, but payload has `currentWeekCompletedCount` / `currentWeekScheduledPastCount` (and prior-week counts). `trainingStatus` is the categorical output. **No single “adherence %” field** today |
| **nutrition compliance** | **Derivable** — `mealCompliance7dPct`: distinct days with `meal_completions` in last 7d ÷ 7 × 100. **Null** when no completions in window (not same as assignments-tab `compliancePct30d`) |
| **last check-in** | **Real** — `metrics.lastCheckinDate` (complete wellness log: sleep + stress + soreness) |
| **last activity** | **Real** — `metrics.lastActive` (max of recent workout completion date vs wellness log date, 7d window for workout leg) |
| **body metrics (weight)** | **Real in DB** (`body_metrics`) — used in alerts elsewhere — **not on list API** |
| **athlete score (0–100)** | **Real when row exists** — `athlete_scores` table; see Part 3 |

## PART 3 — The headline metric (score-ring decision)

### Does a real client score exist?

**Yes — confirmed.**

| Aspect | Detail |
|--------|--------|
| **Storage** | `athlete_scores` table |
| **Computation** | `calculateAthleteScore()` in `src/lib/athleteScoreService.ts` — program-week **adherence × execution** composite (0–100), tier via `getTier()` |
| **When skipped** | No active program, paused program, or no data → **no new row** |
| **Refresh** | Daily cron `src/app/api/cron/daily-sync/route.ts`; also after some workout discard paths |
| **List consumption** | `fetchCoachAthleteScoreSummariesByClientIds` → `client.athleteScore` → `CoachClientListScoreChip` (**returns null when no row**) |

**Populated for real clients?** Partially — 7/11 on sample coach; values exist but can be **stale** and **misleading** (Popescu: score 0 / benched while actively training in July).

Element 16 mock **score ring 80** is **illustrative**; mock meta “Adherence 88%” is **not** a single list field (conflates training + other signals).

### If not relying on score alone (recommended nuance)

| Candidate right-stat | Verdict |
|---------------------|---------|
| **Athlete score ring** | Real composite; **best when row exists**; **null for 36%** of sample roster; **staleness risk** |
| **Week training adherence %** | **Derivable now** from list payload: `round(currentWeekCompleted / currentWeekScheduledPast × 100)` when denominator > 0; **fresh** with training payload; **null** when no program / no past-due slots |
| **Nutrition `mealCompliance7dPct`** | Real but **sparse** (Popescu 0); nutrition-only |
| **Training status label** (“Behind”, “On track”) | Real, categorical — already `CoachClientTrainingStatusBadge`; not a single glance number |
| **Last active relative** | Real (`metrics.lastActive`) — good **non-numeric** fallback |

### Recommendation for Part 3 (audit read)

**Use athlete score as a ring only when `athleteScore != null`**, with tier color (existing `CoachClientListScoreChip` / `tierColorForKey`) — **do not show a fake 0** when null.

**When null:** prefer **week training adherence %** (derived from existing counts, no new schema) **or** muted **“—”** + sublabel, **not** a ring at 0.

**Do not** put mock “Adherence 88%” in meta unless you pick one real definition (week % vs meal 7d vs athlete score) and label it.

Same rigor as program-blocks audit: the **ring is real but incomplete and often stale** — treat null and stale as first-class UX states before build.

## PART 6 — Recommendation

### What the client card should show

**Direct application of Element 16** for shell (dark card, hue rail, right glow, meta line, side stat, icon actions) — **same primitive** as Programs and nutrition rosters.

**Content is more nuanced** than plans/assignments because the list already carries **two status systems** (roster + training), **optional score**, and **rich meta** — closer to the Element 16 *illustrative* client example than to a pure entity rename.

### Right-stat decision (before build)

| Approach | Pros | Cons |
|----------|------|------|
| **A. Athlete score ring only** (current chip) | Real 0–100 composite; already wired | 4/11 null on sample; stale (Popescu); misleading 0 |
| **B. Ring if score, else week adherence %** | Always something meaningful when on program | Two metrics; need clear sublabels |
| **C. Week adherence % only** | Fresh, derivable, no null table gap | Ignores execution multiplier; no row when no program |
| **D. Non-numeric fallback** (training status + last active) | Honest when numbers absent | Less “glanceable” than mock ring |

**Audit pick: B** — ring when `athleteScore != null`; else week adherence % when computable; else muted `—` (mirror nutrition assignments compliance-null pattern). **Do not** default ring to 0.

**Optional pre-build product call:** refresh scores on list load (additive API/cron trigger) vs accept daily staleness — **not required for presentation-only** but affects trust in the ring.

### What to omit

- Structure strip  
- Meal plan name (unless additive fetch approved)  
- Join date, body weight on card (not in list API)  
- Mock composite “adherence %” without definition  
- `coach-04-clients.html` table layout  

### Coherence

Clients as collection cards completes the roster trilogy (Programs ✓, Nutrition plans/assignments ✓, Clients pending). Food DB / exercise catalogs stay tabular elsewhere.

### Mockup for approval?

**Mostly clean direct build** using `CollectionCard` + porting `CoachClientListScoreChip` into `rightStat`.

**Warrant a quick approval pass** if choosing **severity-mapped hue** vs **stable id hue**, or **dual right-stat fallback (B)** — one static mock with Popescu (stale score + active program) and a null-score client avoids mid-build surprise.

Not as novel as program phase strips; **more novel than nutrition cards** due to score null/stale and dual status.
