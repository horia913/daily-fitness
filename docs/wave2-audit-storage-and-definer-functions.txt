1c. DECISION ANSWERS
--------------------

S1 — progress photos: drop "Public can read progress photos"?
  VERDICT: YES, safe to drop for primary app flows — CONFIRMED reads use signed URLs.
  Evidence:
    - Bucket is already private (public=false in storage.buckets).
    - progressPhotoService enriches all fetches with createSignedUrl (lines 53-64).
    - Authenticated scoped policies exist: Clients can read/update/delete own photos
      (foldername[1]=auth.uid()), Coaches can read client photos (clients join).
  Exposure note:
    - The PUBLIC bucket flag is false — the policy is the main anon bypass, not bucket
      publicness. Dropping the policy is the right fix; bucket can stay private.
  Caveats / minimal changes:
    1. progressPhotoStorage Pattern B paths ({recordType}/{clientId}/...) do NOT match
       client folder policy (expects foldername[1]=uid). Coaches rely on
       "Coaches can read client photos" (foldername[1]=client_id) — works for Pattern A
       only. Pattern B needs coach policy extended OR paths normalized.
    2. Remove or stop calling getPublicUrl in progressPhotoStorage.getPhotoUrl (deprecated).
    3. Any legacy progress_photos rows with real public URLs in photo_url (pre-migration)
       need signed-URL migration at render — grep shows placeholder storage:// pattern now.
  Render points already on signed URLs: body-metrics page, ProgressMomentCard (above).

S2 — meal photos: bucket id + path for policy rescope
  Exact bucket id: meal-photos  (CONFIRMED live id=name)
  Policies to scope: meal_photos_delete_own 1o5iea3_0, meal_photos_insert_own 1o5iea3_0,
    meal_photos_select_own_and_coach 1o5iea3_0, meal_photos_update_own 1o5iea3_0
  Required addition to each: AND bucket_id = 'meal-photos'
  Upload path for policy folder check: foldername(name)[1] must equal auth.uid()::text
    Matches code: {clientId}/{mealId}/... — CONFIRMED
  Additional finding: meal_photos_select_own_and_coach allows ANY coach/admin to SELECT
    any object (no clients-table join) — over-permissive even after bucket scoping.
  Legacy getPublicUrl in mealPhotoService + client/progress/nutrition/page.tsx should
    switch to path + createSignedUrl (align with mealCompletionService).

S3 — avatars: path convention for ownership policy
  Actual convention: FLAT files `{userId}-{timestamp}.{ext}` at bucket root — NOT foldered.
  Ownership fix cannot use foldername[1]=auth.uid() — must use e.g.:
    (storage.filename(name)) LIKE (auth.uid())::text || '-%'
  OR migrate uploads to `{userId}/{filename}` and use folder policy.
  Current policies (live):
    Public can view avatars — SELECT, qual: bucket_id='avatars' (public role)
    Users can upload/update/delete — WITH CHECK/qual: bucket_id='avatars' AND
      auth.role()='authenticated' ONLY (no per-user check) — CONFIRMED mismatch
  profiles.avatar_url stores full public URL:
    .../storage/v1/object/public/avatars/{fileName}

S4 — listing restriction on avatars / exercise-images
  grep result: ZERO .list( calls on storage in entire src/
  Exercise UI: reads exercises.image_url from DB (ExerciseCard, ExerciseSelector, etc.)
  Avatar UI: reads profiles.avatar_url (public URL string)
  VERDICT: Restricting storage.objects LIST policies should NOT break current UI.
  Caveat: Supabase advisor flagged public bucket SELECT policies enabling enumeration;
    that is a storage API concern, not img src. No code depends on list today.
