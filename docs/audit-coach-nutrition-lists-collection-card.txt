## PART 2 — Fit assessment (the decision)

### Meal plans — **CONVERT to collection card**

**What a plan carries (real data):**
- **Name** — yes
- **Status** — `is_active` → Active / Draft (not “inactive archive”; draft = not active)
- **Macro targets** — `computed_*` or `target_*` kcal + P/C/F (rich meta line; may show `—` if unset)
- **Meal count** — `meal_count` (meals per day slot count, displayed as `N/day`)
- **Assigned clients** — `usage_count` (assignment row count)
- **No** periodization, weeks, training blocks, or segmented structure

**Verdict:** Strong parallel to **Programs list** (Phase B). Enough for name + status pill + meta line + right-stat (client count) + four actions. **No structure strip** — meal plans have no block/phase analog; omit `structure` entirely.

**Caveat:** `usage_count` counts all assignment rows, not distinct active clients; card should match current semantics unless product wants active-only (would be a logic change — fence).

**Optional gap:** No **avatar initials** for assigned clients in fetch (Programs API added `assignedPreview`). Card can show count-only at zero extra data, or add a small batch preview later (presentation+API additive).

---

### Assignments — **CONVERT to client-forward collection card** (recommended) OR stay table

**What a row is:** Relationship record (client ↔ plan) + operational fields (start, label, compliance, active).

**Client-forward card case (recommended):**
- Element 16’s **Clients roster example** is the pattern: name = client, meta = plan + dates + label, right-stat = compliance %.
- Identity is strong (name + initials already rendered).
- Each row is a **top-level coaching object** (a client’s live nutrition assignment), not a flat join table cell.

**Tabular case:**
- Seven comparable columns (plan, date, label, compliance) favor **scan across many assignments** in one glance.
- Coach with 30+ assignments may prefer dense columns over 30 tall cards.

**Verdict:** **Convert to client-forward collection card** for **coherence with Programs/Plans roster grammar**, if assignment volume stays moderate (typical coach roster). If lists routinely exceed ~15–20 rows, **hybrid**: card default with optional compact table toggle — but that’s product scope; **audit recommendation: convert**, same as plans.

**No structure strip** — no segmented analog.

**Label editing:** Not in this panel today; card build must not imply inline label edit unless added (fence).

---

### Food database — **STAY TABULAR** (explicit UX call)

**What a food is:** Uniform catalog entry — name, brand, category, serving, macros. High count, **comparison-heavy** (scan kcal/P/C/F across rows, filter by category).

**Card per food would be:**
- Sparse (one macro line + category chip — little more than a table row)
- Slower to scan (one card height >> one 58px hairline row)
- Regresses the deliberate open-table Phase B nutrition workspace design

**Verdict:** **Keep open table.** Restyle only if needed (already system-styled hairlines). **Do not force CollectionCard** on foods. This is intentional inconsistency: **roster entities = card; reference catalog = table** — matches Element 16 law (“roster pages” vs in-item sub-lists).

## PART 5 — Recommendation

| Panel | Decision | Why |
|-------|----------|-----|
| **Meal plans** | **→ Collection card** | Top-level roster entity; same richness as Programs (name, status, meta, assigned count, actions). Direct reuse of Phase B patterns. |
| **Assignments** | **→ Collection card (client-forward)** | Each row is a coached relationship with identity + compliance stat; matches Element 16 Clients example. Table was built for scan density but roster grammar favors cards at coach scale. |
| **Food database** | **→ Stay open table** | Reference/catalog data; uniform rows; macro comparison; high volume. Cards would be sparse and harm scan — **not** a “plain list regression” but the correct control for catalog search. |

**Coherence statement:** Plans + Assignments as **collection cards** + Foods as **dense open table** is consistent with the design system law: Element 16 for **top-level roster entities**; Element 06-style open rows for **uniform searchable catalogs**. Nutrition workspace tabs then mirror Training: Programs (cards) vs Exercises (likely table elsewhere).

**Decide before build (not mid-build):**
1. Meal plan `usage_count` — keep all assignments vs active-only for right-stat?
2. Assignment card — compliance as right-stat number vs mini ring?
3. Whether to add `assignedPreview` initials for meal plans (optional; count-only is fine v1).
4. Shell width — nutrition still `data-7xl`; align to `canvas-full` separately if desired.

**Awkward-risk flag:** Assignments **only** if a coach has very large assignment lists (50+), a card stack may feel long; table excelled at 7-column scan. Monitor with real data; table fallback is a product escape hatch, not required for v1.
